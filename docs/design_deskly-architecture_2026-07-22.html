対象: 全社横断（なまけもの / WF / Nextcloud）

Nextcloud Tables を全社共通 QA 管理サービスに

2026-07-22 / owner: ishizakahiroshi / 対象読者: 経営判断側・実装者
社内システムごとにバラバラだった問い合わせ管理を、Nextcloud Tables 1 テーブルに一元化する構想。既存の自社 Nextcloud（drive.mercury-group.co.jp）を使うため 他社クラウドに一切データを預けず、実装コスト最小、AI エージェント連携も MCP 経由で即接続できる。
前提: 対象ユーザー（肥尾さん / 石坂 / 上之薗 / その他社内開発者）は全員 Nextcloud アカウントを保有済み。認証・権限・通知は Nextcloud 標準機能を利用し、独自ユーザー管理は一切作らない。
  • Mercury グループでは約 30 名が既に日常的に Nextcloud を利用中（勤怠関係者・肥尾さん含む）
  • Mercury 社員のユーザー ID は mercury_<社員番号> 形式で統一（例: mercury_100000230）。数値部はなまけものの employee_id と一致するため、起票者列の名前解決と kb people 台帳照合が自動でつく
  • 石坂・上之薗は外部ベンダー扱いの別ドメインアカウント。Tables の権限グループは「mercury_ 社員 + 開発ベンダー」の 2 グループで組む（Nextcloud 標準 Group で表現可）
  • 通知は Nextcloud Talk / メールで 対応者列の社員 ID にそのまま飛ばせるため、通知系統の独自実装は不要

全体像

各業務システム（なまけもの / WF / Nextcloud 本体）に「QA 起票ボタン」を配布し、押すと Nextcloud Tables の中央 1 テーブルに行が追加される。開発者と AI エージェントは同じ 1 テーブルを見る。

起票フロー（肥尾さん視点）

なまけものの画面右上には環境ラベル（「開発環境」「検証環境」「本番環境」）が既にある。ここにホバーすると、その環境に今デプロイされている版情報がポップオーバーで出る。ポップオーバー内の「QA に起票」ボタンを押すと、環境・版 SHA・起票者が既に埋まった状態で Nextcloud Tables の新規行画面が開き、肥尾さんは本文（症状）だけ書けば OK。

3. ボタンを押すと Nextcloud Tables に prefill 済みの行が作られる

「📤 QA に起票」を押すと、REST API で新規行を作り、そのまま Nextcloud Tables の該当行編集画面が新タブで開く。日付・システム・環境・版・起票者は既に埋まっているので、肥尾さんは 「内容」列に症状を書くだけ。

なぜ Nextcloud Tables を選ぶか

案 初期コスト 保守コスト 肥尾さん UX AI 連携 クラウド方針 判定
A. なまけもの内に QA 画面 + 自作 DB 1〜2 週間 永続的に発生 要学習 要 API 自作 自社内 OK 重い
B. kb に CSV/xlsx 追加 数時間 低 肥尾さんが触れない（致命） grep 可 ローカル完結 不可
C. Google Sheets（現状） ゼロ 低 慣れている gspread 他社クラウド NG 経営方針で×
D. Nextcloud + OnlyOffice で xlsx 1 日 低 Sheets 相当 WebDAV 経由 自社内 OK 中間解
E. Nextcloud Tables + REST + MCP 2〜3 日 Nextcloud に同居 Web で編集 MCP 直結 自社内 OK 推奨

D 案（xlsx）でも足りるが、Tables の方が列定義・API・Webhook・検索フィルタが構造化されている分、各システムからの起票ボタン配線と AI エージェント連携が素直に書ける。既存の xlsx の QA シートは Tables にそのまま列マッピングして移行可能。

実装段階

STEP 1

Nextcloud Tables 準備

  • 「システム問い合わせ管理」テーブル作成
  • 列定義を確定
  • 既存 QA シート内容を移行
  • 関係者に共有権限付与
STEP 2

なまけもの版情報 + 起票ボタン

  • deploy スクリプトで VERSION 書出し
  • version.php endpoint 新設
  • 環境ラベルにホバーポップオーバー
  • 「QA に起票」ボタン → Tables API
STEP 3

AI エージェント経路（MCP）

  • Nextcloud MCP を Claude Code に配線
  • Tables 読み書き権限テスト
  • 「未対応の質問ある？」に即答できるか検証
STEP 4

他システム展開

  • WF に同型の起票ボタン配布
  • Nextcloud 本体にも起票入口
  • 再利用可能な JS スニペット化
  • 横断ダッシュボード作成

STEP 1 + 2 で 2〜3 日、STEP 3 で追加 0.5 日、STEP 4 は必要になったシステムから随時。 STEP 1・2 が終わった時点で「今回の 7/21 バグと同種の問い合わせ」は既に効率化される。

リスクと対策

1. Nextcloud Tables のバージョン依存

Nextcloud 本体を大きくアップデートする際、Tables アプリの互換性を事前確認する必要がある。→ Nextcloud アップグレード運用に「Tables 動作確認」を組み込む。

2. Tables の API レートリミット

起票ボタン頻度は 1 日数十件想定なので実運用では問題にならない。将来的にアラート系や外部連携で大量起票が発生する場合は、キューを挟むかバッチ集約する。

3. Google Sheets からの移行漏れ

過去分の QA 履歴を Tables に持ってこないと、肥尾さん側で「以前の指摘を検索できない」問題が発生。→ STEP 1 の中で全件マイグレーションを含める（xlsx 落として Tables インポート）。

次のアクション

  1. 本構想の 方針 GO / NG 判断（経営側）
  2. Nextcloud Tables アプリの有効化状況を drive.mercury-group.co.jp で確認
  3. GO なら plan md を起こす（STEP 1・2 の詳細タスク分解、担当・期日）
  4. STEP 1・2 実装（想定 2〜3 日）
